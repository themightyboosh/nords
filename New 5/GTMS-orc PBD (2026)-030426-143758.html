ore PBD (2026)


  1. Vision / Goal

    ore is the Org Activity Capture and Intelligence Platform for GTM Engineering. It serves as the canonical store for all organizational activity - what happened, who did it, when, what it relates to, and where the source material lives. ore replaces the hierarchy as the information routing layer by making the org fully legible and queryable.

    The governing principle: agents read and write from one place. Humans use whatever tools they already use. A distribution layer bridges the two. Nobody changes behavior. The org just becomes visible.

    ore is not a dashboard. It is not a reporting tool. It is the org's memory - structured, linked, and queryable by humans and agents alike.

  2. Context I Problem


    Problem

    Description

    Signal loss in meetings

    Meetings are recorded but decisions, commitments, and context are not extracted into any structured system. The richest signal the org generates decays immediately.

    Hierarchy as information filter

    Managers relay information up and down the chain. This relay is lossy, politically biased, and slow. The hierarchy optimizes for the game players, not the builders.

    Fragmented activity trail

    Work happens across GitHub, Jira, Confluence, Teams, and email. No single system links these into a coherent picture of what the org is doing.

    Agent context starvation

    Agents can execute tasks but lack shared understanding of the org's domain, decisions, and ways of working. Each agent is built with bespoke context instead of reading from a common model.

    Invisible decisions

    Most decisions happen in conversations and are never recorded. When someone asks "when did we decide X," no one can answer without archaeology.


    Consequence

    Impact

    Status meetings persist

    Humans attend meetings to relay information that should be queryable. Builder time is consumed by the relay function.

    Repeated mistakes

    Decisions made and forgotten get relitigated. Context built once disappears and must be rebuilt.

    Agent sprawl

    Every new agent requires hand-coded domain knowledge instead of reading a shared ontology. Agent creation is expensive when it should be cheap.

    Leadership blind spots

    Leaders see curated narratives, not ground truth. The org's actual state is opaque above the IC level.


    The opportunity: if org activity is captured, structured, and linked in one canonical store, every human and agent in the system can query the org's actual state without going through the hierarchy. The relay function of middle management becomes unnecessary. Builder time is reclaimed. Agents become cheap to build because context is cheap to read.


  3. Solution Overview

    ore sits between humans and their existing tools. It does not replace any tool. It indexes what happens across those tools, structures the activity into an ontology, and makes it queryable.

    The system has three zones:


    Agent Zone - All agents read and write exclusively to the canonical store (Postgres + S3). They do not interact with external systems. Their tool surface is minimal: read from store, write to store. This is where all intelligence happens.

    Human Zone - GitHub, Jira, Confluence, Teams, and whatever else humans already use. Nothing changes for humans. They keep working in their existing tools.

    Distribution Layer - A single agent that bridges the two zones. It reads from the canonical store, translates to the appropriate format, and pushes to human systems (Confluence pages, Jira updates, Slack notifications). It also ingests from human systems - a Jira ticket created by a human becomes a pointer in the canonical store via webhook.

    The key constraint: agents never need to know about external systems. The distribution agent is the only component with external system knowledge. Swap out Confluence for something else and no agent notices.

    Risk

    Mitigation

    Capture discipline degrades

    Automated capture (webhooks, Copilot integration) minimizes reliance on human discipline. Monitor capture coverage metrics.

    Store becomes a data swamp

    Strict write contract enforced by the APL Monthly archive cycle keeps active index lean. Ontology provides structure.

    Distribution agent becomes a bottleneck

    Single-concern design. If it fails, the canonical store still functions - human systems just don't get updates until it recovers.

    Postgres cost scales unexpectedly

    Volume is bounded by org size (~50-100 people). Structured records are small. Bulk content lives in S3. Cost risk is minimal.

    LLM inference costs from query layer

    Model calls only happen on natural language queries requiring synthesis. Structured queries (joins, traversals) hit Postgres directly. No embedding pipeline unless explicitly added later.

    Team can't build it in a week

    Design is intentionally simple. Postgres, S3, a write AP!, one distribution agent, markdown everywhere. If four people can't build this in a week, the process is broken.

ore FBD: Canonical Store


  1. Vision / Goal

    The Canonical Store is the single source of truth for all org activity. Every meaningful action - a decision made, a ticket created, a meeting held, an artifact produced - is a structured record in Postgres with bulk content in S3. The store is an index of what happened, not a copy of everything. It links to content where it lives and compounds over time into a complete, traversable trail of the org's operating history.

  2. Context I Problem


    Problem

    Description

    No unified activity record

    Work happens across GitHub, Jira, Confluence, and Teams. No system links them. Asking "what happened with X" requires human archaeology across five tools.

    Agent write fragmentation

    Agents produce output to various destinations with no consistent structure. Each agent decides independently where and how to store results.

    Stale dashboards

    Traditional BI requires predefined queries. If nobody built the dashboard for a question, the question can't be answered.


    Consequence

    Impact

    Context rebuild cost

    Every new conversation starts from zero. Decisions, commitments, and history must be manually reconstructed.

    Agents can't share context

    Agent A's output is invisible to Agent B. Each agent operates in isolation.

  3. Solution Overview

    Postgres holds the structured index. S3 holds the bulk content. Together they form the canonical store.

    A record in Postgres is small: entity type, actor, timestamp, domain, relationships (foreign keys), source URL, and a brief summary. If the content is agent-authored, it lives as a markdown file in S3 and the Postgres record points to the S3 key. If the content is human-created in an external system, the Postgres record links to it (GitHub PR URL, Jira ticket URL) and the content stays where it was born.

    The write API enforces the schema. Nothing enters the store without conforming to the write contract.

  7. Capabilities


    1. Write API


      Thin HTTP API that enforces the write contract. Accepts a structured record, validates against the schema, writes to Postgres, optionally stores markdown content in S3. Returns the entity ID

      and confirmation.


      Features:

      • Schema validation before write

      • Automatic timestamp if not provided

      • S3 content upload with key generation

      • Idempotency support (dedup on source_url + timestamp)

      • Batch write support for bulk ingestion


    2. Read API


      Query interface for agents and the query layer. Supports structured queries (by domain, entity type, time range, actor) and relationship traversal.

      Features:

      • Filter by domain, entity_type, actor, time range

      • Traverse relationships N hops deep

      • Return S3 content inline or as presigned URL

      • Pagination for large result sets


    3. Schema Registry


      Defines valid entity types, relationship types, and domain scopes. The source of truth for what can be written to the store. Agents and the ontology system reference this.

      Features:

      • Entity type definitions with required/optional fields

      • Relationship type constraints (which entity types can relate to which)

      • Domain registry with ownership metadata


    4. S3 Content Management

      Handles markdown content storage, retrieval, and lifecycle. Features:

      • Write markdown to structured S3 path

      • Retrieve content by entity ID (lookup S3 key from Postgres)

      • Presigned URL generation for direct access

      • Lifecycle policy: transition to IA after 90 days, Glacier after 365


    5. Pointer Records


      For content living in external systems, the store holds a structured pointer - not a copy.

      Features:

      • Source URL validation (ensure the link is well-formed)

      • Metadata extraction from URL patterns (e.g., GitHub PR number from URL)

      • Relationship linking (pointer to a PR relates to the work_item entity it implements)

    Write AP! becomes a bottleneck

    Orphaned records (no relationships)

ore - Ontology System FBD

ore FBD: Ontology System


  1. Vision / Goal

    The Ontology System defines what the org knows about itself - the entity types, the relationship types, and the domain scopes that give structure to the canonical store. When an agent needs to understand what a "decision" is, how it relates to an "event," or what domains exist in the org, it reads the ontology. The ontology is the shared context that makes every agent in the system domain-aware without encoding domain knowledge into each agent's prompt.


  2. Context I Problem


    Problem

    Description

    Agents lack shared vocabulary

    Each agent is built with bespoke understanding of the domain. One agent knows what a "deal" is, another doesn't. There's no common model.

    Relationship types are ad hoc

    When agents link things together, the relationship semantics are inconsistent. "relates_to" means different things to different agents.

    New agents are expensive

    Standing up a new agent requires teaching it the domain from scratch. Context that should be read from a model is instead hardcoded in prompts.


    Consequence

    Impact

    Inconsistent capture

    Without agreed entity types, the same activity gets classified differently by different agents or at different times.

    Untraversable relationships

    If relationship types aren't constrained, you can't reliably ask "show me all decisions that led to this work item."

    Agent sprawl

    Each new agent carries its own domain model, creating maintenance burden and drift.


  3. Solution Overview

    The ontology is a set of tables in Postgres that define the vocabulary of the canonical store. It is not a separate system - it lives alongside the activity data and constrains what can be written.

    Two ontology scopes exist:


    Org Activity Ontology - how work happens. Entity types: people, work items, decisions, artifacts, events, communications. This is the v1 scope and the focus of this FBD.

    Business Domain Ontology - what the work is about. Entity types: deals, policies, service functions, customers, capabilities. This is a future scope, built in BDlytics, that converges with the org activity ontology when both are mature.

    The org activity ontology ships first because it's prerequisite to capture. You can't capture what you haven't defined.

ore - Agent Framework FBD

ore FBD: Agent Framework


  1. Vision / Goal

    The Agent Framework defines how agents interact with the canonical store. Every agent in the system - regardless of purpose - reads and writes through a single interface. Agents do not know about external systems. They do not know about Confluence, Jira, GitHub, or Slack. They read from the store, they write to the store. That's it. This constraint is what makes agents cheap to build and easy to replace.


  2. Context I Problem


    Problem

    Description

    Agents have fat tool surfaces

    Current agents carry tools for Confluence, GitHub, Jira, Slack - each with auth, pagination, error handling. Most of the agent's complexity is integration, not intelligence.

    Each agent is a snowflake

    Agents are hand-built with custom context, custom tools, custom output formats. There's no standard pattern for how an agent reads context or writes results.

    Agent replacement is expensive

    Swapping a model or changing an agent's scope requires reworking its entire tool surface and context injection.


    Consequence

    Impact

    Slow agent development

    Building a new agent takes days because of integration plumbing, not intelligence design.

    Fragile agents

    External AP! changes break individual agents. A Confluence AP! update affects every agent that publishes there.

    Context duplication

    Multiple agents embed the same domain knowledge in their prompts instead of reading it from a shared source.


  3. Solution Overview

    The agent framework enforces a single constraint: agents interact only with the canonical store. An agent's tool surface is exactly two categories:

    • Read tools - query the store, read the ontology, fetch artifact content from S3

    • Write tools - create entity records, create relationships, store artifact content


    Everything else - publishing to Confluence, updating Jira, posting to Slack - is the distribution agent's job. The building agent doesn't care where its output ends up. It writes a structured record and markdown content to the store. Done.

    This also means agent context comes from the store, not from prompts. An agent reads the ontology to understand entity types. It reads recent activity records to understand current state. It reads related artifacts for detailed context. The prompt tells the agent what to do. The store tells the agent what it needs to know.

ore - Distribution Layer FBD

ore FBD: Distribution Layer


  1. Vision / Goal

    The Distribution Layer is the single bridge between the agent zone and the human zone. One agent, one concern: move information between the canonical store and the tools humans use. It publishes agent output to Confluence, links activity to Jira tickets, posts notifications to Slack. It also ingests from human systems - a Jira ticket created by a human becomes a pointer record in the canonical store.

    No other agent in the system knows about external systems. All integration complexity lives here.

  2. Context I Problem


    Problem

    Description

    Integration logic scattered across agents

    Today, individual agents carry Confluence tools, GitHub tools, Jira tools. Each one handles auth, pagination, error recovery independently.

    External AP! changes break multiple agents

    A Confluence AP! update requires patching every agent that publishes there.

    Human activity isn't captured

    Work that humans do in Jira, Teams, and GitHub is invisible to the agent zone. There's no pipe from human systems into the canonical store.


    Consequence

    Impact

    Maintenance burden

    N agents times M external systems = NxM

    integration points to maintain.

    Inconsistent pubication

    Different agents format Confluence output differently. There's no consistent presentation layer.

    Incomplete org picture

    The canonical store only knows about agent-generated activity. Human-generated activity is a blind spot.


  3. Solution Overview

    The distribution agent runs on a poll cycle. It reads new or changed records from the canonical store and publishes them to the appropriate human system based on entity type and domain. It also listens for webhooks from human systems and writes pointer records back to the store.

    Outbound (store to human systems):

    • New artifact with domain=proposal-hub ➔ publish to Proposal Hub Confluence space

    • New decision record ➔ post summary to relevant Teams channel

    • New work_item ➔ verify Jira ticket exists, link if so, create if needed


      Inbound (human systems to store):

    • Jira ticket created/updated ➔ write pointer record to store with metadata and relationships

    • GitHub PR opened/merged ➔ write pointer record with branch, author, linked work items

    • Teams meeting completed with Copilot summary ➔ write structured meeting record (see Meeting Capture FBD)

    The distribution agent is the only component with credentials for external systems. No other agent has Confluence auth, Jira auth, or GitHub tokens.

  7. Capabilities


    1. Outbound Publication Engine

      Reads new records from the canonical store and publishes to target systems. Features:

      • Poll-based cycle with configurable interval (default 5 minutes)

      • Distribution rules engine (entity_type + domain to target + format)

      • Formatters per target system (markdown to Confluence, markdown to Slack, etc.)

      • Publication confirmation written back to source record

      • Retry with exponential backoff on failure

      • Dead letter queue for records that fail after max retries


    2. Inbound Capture Handlers

      Receives webhooks from human systems and writes pointer records to the store. Features:

      • Webhook endpoints per source system (Jira, GitHub, Teams)

      • Metadata extraction from webhook payloads

      • Automatic relationship linking via conventions (branch name contains ticket ID, PR references work item)

      • Deduplication (same event received twice doesn't create duplicate records)


    3. Formatter Registry

      Pluggable formatters that translate canonical store content into target system formats. Features:

      • Confluence formatter (markdown to Confluence storage format with proper macros)

      • Slack formatter (markdown to Slack block kit)

      • Jira formatter (entity metadata to Jira issue fields)

      • Each formatter is a single function - easy to add, easy to test


    4. Distribution Rules Engine

      Configurable rules that determine where records get published. Features:

      • Rules defined in Postgres (not hardcoded)

      • Match on entity_type, domain, metadata patterns

      • Multiple targets per record (an artifact might go to both Confluence and Slack)

      • Override rules for specific domains or entity types

      • Dry-run mode to preview where a record would be distributed without publishing

    Mitigation

    Webhook floods during bulk operations

    Rate limiting on inbound handlers. Batch processing for pointer record creation.

    External API rate limits

    Per-system rate limit awareness in the publication engine. Spread publications across the cycle.

    Format drift (Confluence API changes)

    Formatters are isolated functions. API change affects one formatter, not the whole system.

ore - Meeting Capture FBD

ore FBD: Meeting Capture


  1. Vision / Goal

    Meeting Capture turns the org's highest-volume, highest-value signal source into structured records in the canonical store. Teams Copilot already transcribes and summarizes meetings. Today those summaries sit in Teams and rot. Meeting Capture routes them into the store as structured event records - attendees, date, topics, decisions, action items, link to the recording. Nobody changes behavior. They keep having meetings with Copilot on. The system captures the signal quietly.


  2. Context / Problem


    Problem

    Description

    Meetings are the richest signal source and the most lossy

    A deal review happens, six decisions get made, three action items are assigned. None are captured in a structured system. The recording exists but nobody watches it. The summary exists but nobody links it to anything.

    Decision archaeology

    When someone asks "when did we decide X," the answer requires a human to remember which meeting it was, find the recording, scrub through it, and hope the decision was stated clearly.

    Action item black hole

    Commitments made in meetings are not tracked. They exist in someone's memory or in a Copilot summary that scrolls away.


    Consequence

    Impact

    Decisions relitigated

    Without a record, the same decisions get debated repeatedy.

    Commitments dropped

    Action items assigned in meetings have no enforcement mechanism. They disappear



    unless someone manually tracks them.

    Context evaporates

    The nuance behind a decision - the tradeoffs considered, the options rejected - is lost the moment the meeting ends.


  3. Solution Overview

    Teams Copilot produces structured meeting summaries via the Microsoft Graph APL Meeting Capture is a pipeline that:

    1. Detects when a meeting with Copilot completes

    2. Retrieves the Copilot summary via Graph API

    3. Parses the summary into structured components (attendees, topics, decisions, action items)

    4. Creates an event record in the canonical store

    5. Creates linked decision records for each decision identified

    6. Creates linked work_item records for each action item identified

    7. Stores the full transcript/summary as a markdown artifact in S3

    8. Links all records to the relevant domain and to the people who attended


    The output: one event record, N decision records, M work_item records, one artifact, all linked. The meeting is now fully represented in the canonical store and queryable.

    Pipeline Flow

    Decision and Action Item Extraction


    Copilot summaries typically include structured sections for decisions and action items. The pipeline parses these directly when available. When the summary is less structured, an LLM extraction pass identifies:

    • Decisions: statements of choice or direction (e.g., "We decided to go with option B")

    • Action items: commitments with assignees (e.g., "Lead will update the schema by Friday")

    • Topics: subjects discussed (used for domain tagging)


The LLM extraction is a tailback, not the primary path. Copilot's structured output should be preferred when available to minimize inference cost.

Domain Assignment


Meetings are tagged to a domain based on:

  1. Meeting subject line keywords (e.g., "Proposal Hub" maps to proposal-hub domain)

  2. Meeting organizer's domain affiliation (from person records in the store)

  3. Teams channel the meeting was created from (if applicable)

  4. Manual override via meeting subject convention (e.g., "[GTME] Weekly Standup")

      Retrieves Copilot output and parses into structured components. Features:

      • Structured parser for Copilot's decision/action item sections

      Creates the full set of linked records in the canonical store. Features:

      • Decision records extracted from summary, linked to event

    Mitigation

    Meeting volume creates noise

    Decision extraction hallucination

    Confidence scoring on extracted decisions. Review queue for low-confidence items.

    Privacy concerns

    Meeting capture scoped to team/org channels, not personal meetings. Attendee consent through Copilot's existing consent model.
